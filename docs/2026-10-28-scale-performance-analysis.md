# 5,000 规则 × 1,000 文件 × 10 万行：性能优化方案（唯一维护版本，2026-10-28）

> 输入假设：规则集 **5,000+ 条**；**1,000 个压缩文件**；每个文件**最多 100,000 行**；合计 **1 亿行**。
> 分析对象：`service/` 当前 Worker 解析链路（`TaskProcessor` → `scan_archive` → `evaluate_line` → `PostgresMatchWriter`）。
> 数据来源：仓库内 `data/_bench/report-*.json`（既有 5,000 规则全链路基准）、本轮新增 1/4 Worker 复测、以及基于真实 `evaluate_line` 的微基准。
> 相关质量发现：Q-02（命中无上限）、Q-03（队列缺索引）、Q-12（结果保留/分区）、Q-13（热点函数）。
> 修订状态：本文件是唯一持续维护的性能优化方案，废弃实施草案已移除。2026-10-28 已批准并开始独立 B 路线原型；生产 Worker 与参考求值器不变。前五节为基线，第六节以后为路线与验收要求；原型进展见第十五节，生产部署形态（≥5 台 16 vCPU/32 GiB Linux Worker 池、Windows 仅开发、目标 8 小时）与实施顺序见第十六节，不承诺固定加速倍数。

## 一、结论（先看这段）

1. **首要问题是每行遍历全部规则。** 当前 5,000 条规则 × 1 亿行意味着 **5,000 亿次规则访问**；单条正则成本还受模式和行内容影响，不存在仅凭规则数量确定的时间复杂度上界。没有多模式预过滤或 Worker 编译缓存。
2. **当前数据支持优化评测热路径，但不支持承诺固定倍数。** 50 规则既有全链路吞吐为 33,750–41,858 行/s；5,000 规则既有吞吐为 328 行/s（任务处理跨度口径约 340）。不同端到端场景的文件规模和命中密度不同，不能由二者直接证明严格线性；同样本微基准才支持近似线性趋势。
3. **1 亿行的基线外推跨度很大。** 按既有 2 Worker 吞吐约 82–85 小时，本轮 4 Worker 为约 201 小时，1 Worker 为约 544 小时；均未实际跑满 1 亿行。负载波动原因未定位，不能断言是降频，也不能保证加 Worker 线性扩展。
4. **推荐“原生多模式筛选＋原 `regex` 精确复核”。** 重点比较 VectorScan/Hyperscan 的每模式单次命中、AC 的有界候选生成，以及原生逐行批处理；关键词可依据字面量命中集合直接计算 any/all，正则只在可证明的候选超集上复核。详细路线见第六至九节，实测结果与实施顺序见第十五、十六节。
5. **必须同时覆盖结果吞吐。** 合成基准命中密度为 **46,556 / 20,000 = 2.3278 条/行**；若真实负载相同，一亿行会输出 2.3278 亿条记录。按假设 300–500 B/记录仅行数据约 70–116 GB，索引、WAL、备份另计；必须实测实际表大小和持续写入能力。
6. **不以准确性换速度。** 不删除重复规则、不减少超时预算、不截断结果来制造提速；旧方案的正则 hint 已复现漏报，不能沿用。5×、10× 或 4 小时完成都只能是待测目标，而不是现有证据支持的承诺。
7. **生产规模是 ≥5 台 16 vCPU/32 GiB Linux Worker 池，Windows 仅开发。** 按 8 小时窗口反推，每进程只需 69.4 行/s，而单进程参考评测实测 274 行/s（P0 后）：**CPU 口径上今天就够，不需要为达标而重写匹配算法。** 但实测拆解同时表明每任务非评测开销只有约 40 ms，端到端时间几乎全在逐行评测里（3.93 ms/行），所以扫描优化的收益直通端到端：它把 8 小时从约 3.7 小时（40 进程、含并行折损）变成数十倍余量，并抗住密集命中与超长行。完整容量模型、跨平台契约与验收矩阵见第十六节。

## 二、当前代码路径与复杂度

### 2.1 每行做什么

`TaskProcessor.process`（`processor.py:171`）逐行读取 `scan_archive` 的 `LineRecord`，对每个成员先做 `file_glob` 判断，然后调用：

```python
matches = evaluate_line(self._rules, line.text, line.line_no)
```

`evaluate_line`（`evaluator.py:113`）对 **每一条规则** 执行：

1. `rule.enabled` 判断；
2. 关键字规则：`_keyword_hit` → 大小写不敏感时 **每条规则各调一次 `line.lower()`**，再对 `any`/`all` 词表逐个 `in`；
3. 正则规则：`item.regex.search(line, timeout=timeout_ms/1000)`；
4. **每条规则先分配一个 `fields = {}`**，即使不命中；
5. 命中后构造 Pydantic `RuleMatch`，再在 processor 里构造 `MatchRecord`、截断 `raw_line`、追加批次。

复杂度：

```text
总规则-行比较次数 = 总行数 × 启用规则数
                = 100,000,000 × 5,000
                = 5.0 × 10^11
```

若仅按观测区间 **0.8–4 µs / 规则-行** 粗算，5,000 亿次访问约为 **111–556 小时单核等价**。这只是不同负载状态下的量级换算，不是可保证的下限，也未证明慢状态来自降频；最终以完整链路实测为准。

### 2.2 规则编译没有缓存

- `WorkerRuntime` 每个任务都调用 `self._rules_factory(task)`（`worker/main.py:138`）；
- 默认 `_compile_task_rules` 每次执行 `RuleSetConfig.model_validate` + `compile_ruleset`（`worker/main.py:34`）；
- 实测 5,000 规则：**解析 10.8 ms + 编译 234 ms/任务**；
- 1,000 个文件 → **234 秒（约 3.9 分钟）** 纯编译开销。相对 27–82 小时的总时长很小（<1%），但完全没有必要；设计 §8.1 明确要求按 `rule_set_id` 缓存编译结果和 AC 自动机。

### 2.3 设计 vs 实现

| 设计 §8.1 要求 | 当前实现 | 影响 |
|---|---|---|
| 关键词规则用 Aho-Corasick 一次性扫描 | 每条关键字规则逐行 `lower()` + `in` | 2,010 条关键字规则 ≈ 1.0 ms/行 |
| 正则规则只在候选行上执行 | 所有 2,990 条正则对每一行 `search` | ≈ 2.8 ms/行（5k 混合基准） |
| Worker 进程内按 `rule_set_id` 缓存编译规则/AC | 每任务重新 parse + compile | 234 ms/任务，1,000 任务约 3.9 分钟 |
| 命中按批写库 | 已实现，1,000 条/批；SQLAlchemy `insert` | 可用；高命中率时可进一步评估 COPY |
| `matches` 按月分区/保留期 | 未实现 | 2.33 亿行时清理和查询都困难 |

### 3.2 单核微基准（真实 `evaluate_line`，128 B/行）

规则数与耗时基本线性。进一步拆分 5,000 规则：

| 子集 | 规则数 | 吞吐 | 每行耗时 |
|---|---:|---:|---:|
| 全量混合 | 5,000 | 247 行/s | 4.04 ms |

### 4.1 每文件耗时

100,000 行/文件：

| 单 Worker 吞吐 | 每文件耗时 |

以实测锚点直接换算（1 亿行 ÷ 聚合行/s）：

| 配置 | 实测聚合吞吐 | 1 亿行耗时 | 说明 |
|---|---:|---:|---|

> 理想线性是容量假设，不是保证或严格上界。扩容必须在固定 CPU/内存配额的目标宿主验收，记录数据库和存储是否共享竞争资源。

### 4.3 行宽需要独立验证

平均行宽、p99 行宽和超长行比例都会影响扫描及内存。撤回由顺序微基准推导的 2.6× / 6.5× 倍率与“50 天”预测；第十二节采用交错重复实验重新验证。

### 4.4 命中量放大

基准是 2.33 条/行。若规则更宽（多个关键字重叠、`.*`、空关键字），命中率可能到 5–20 条/行：
- 5 条/行 → 5 亿行 `matches`；
- 20 条/行 → 20 亿行；
- 磁盘、索引、写入、清理压力随结果量增加；是否先于 CPU 成为瓶颈仍需实测。`max_matches_per_task` 目前没有执行点。

**完整性约束：** 按此合成密度，单个十万行文件约输出 233,000 条命中，超过配置默认值 200,000。不能为了达到性能目标而直接启用截断、删规则或提高/降低该上限；结果上限、partial 与超时后的业务行为必须另行确认，本方案不改变这些语义。

## 五、瓶颈排序（5,000 规则，当前代码）

1. **逐规则评测**：本样本 profiling 的主要耗时；独立微基准中正则约占 70%、关键字约占 25%，不能把这些比例与 profiler 嵌套时间再次相加。
2. **Python 循环与对象开销**：重复 `lower()`、类型分派、字典分配均在热路径，属于上述评测成本的一部分。
3. **编译未缓存**：约 234 ms/任务 × 1,000 = 3.9 分钟，相对数十小时很小，不是数量级提速来源。
4. **宿主与并发**：本轮两次运行的 4/1 Worker 吞吐比为 2.7，必须控制资源配额重新验证扩展曲线。
5. **结果写入**：优化后瓶颈可能迁移至写入、序列化或索引；高命中密度必须纳入同一端到端验收。
6. **复制与解压**：当前约 42 KB 压缩包样本不支持排除 GB 级包、NAS 与解压的瓶颈。

## 六、性能优先的三条路线

**建议：以 B 为主线，A 为可移植的验证基线，C 仅在确认 Python 边界开销后推进。引入成熟原生匹配库，不重写通用正则引擎。**

| 路线 | 核心做法 | 性能价值 | 代价与边界 | 建议 |
|---|---|---|---|---|
| A：AC＋原 `regex` | 多关键词扫描、已证明安全的正则字面量条件、编译缓存 | 移除大量无效规则调用，接入成本低 | AC 位置枚举仍可能膨胀；必须限制中间结果并可回退 | 作为对照与可移植实现，不照搬旧方案的返回全列表接口 |
| B：VectorScan/Hyperscan＋原 `regex` | 原生多模式库扫描字面量；每模式每行最多报告一次；关键词直接判定、候选正则精确复核 | 同时降低规则访问量、重复事件和解释器调用，是重点优化方向 | CPU/平台/wheel/许可证要验证；不能直接替换现有正则语义 | 优先原型验证，正确性和真实负载吞吐双门禁 |
| C：薄原生批处理层＋B | C/C++ 或 Rust 封装成熟扫描库，原生回调写位图，一次跨语言调用处理多行 | 当 Python 回调、对象和调用次数成为主因时进一步提升 | 增加构建发布成本；仍保留原 `regex` 捕获与阈值路径 | 仅在 profiling 证实瓶颈后实施，不先重写整个 Worker |

不优先选择：把所有正则合成一条大正则、直接全部换 RE2/Rust regex、逐行跨进程 RPC、先引入 GPU/Spark。它们分别有规则身份/优先级、语义兼容、通信开销或部署复杂度问题，当前没有收益证据。

## 七、第三方库选型：能力与限制

| 库/组件 | 可利用能力 | 准确性或性能限制 | 定位 |
|---|---|---|---|
| `regex`（现有） | 当前 `search`、named groups、Unicode、阈值前字段抽取与超时语义 | 每行逐条调用昂贵；通用回溯模式没有统一低延迟保证 | 精确参考引擎，第一阶段保留 |
| VectorScan / Hyperscan | 多模式原生扫描、纯字面量编译、`SINGLEMATCH` | 语法类似 PCRE 不等于 Python `regex`；不提供当前捕获/贪婪语义；预过滤保证也不是跨引擎保证 | 重点候选引擎，不直接产生正则最终结果 |
| Python `hyperscan` 绑定 | 0.9.1 提供 `compile(literal=True)`、single-match 与 ID 回调 | 绑定所链接内核、回调/GIL 与平台包需分别核验；literal 长度存在 NUL 截断风险 | 先用于原型，特殊字面量走兼容通道 |
| `ahocorasick-rs` | 原生多字面量匹配；当前已验证 1.0.3 的重叠匹配接口 | `find_matches_as_indexes` 返回完整列表；去重发生在物化之后，不能靠 `set` 控制峰值 | 低重复负载对照；使用现有接口必须先限制输入/模式规模并保守回退 |
| `pyahocorasick` | C 实现、多模式字面量、迭代接口 | 迭代可避免一次物化全部位置，但总事件数仍随重复出现次数增长 | 可移植备选；需事件预算和正确回退，不自动等于最快 |
| RE2 / Rust `regex`、`RegexSet` | 受限正则语法、多模式存在性查询或稳定的搜索复杂度模型 | 回溯引用、lookaround、Unicode/flags/捕获行为不完全兼容；编译成功不等于语义一致 | 仅评估经证明等价的子集，不作全量替换 |
| PyO3 / Cython / C API | 原生批处理、位图、减少 Python 回调 | 是集成工具，不会自动降低正则算法复杂度 | C 路线中的薄封装，优先复用库而不是自研引擎 |
| `psycopg` COPY（已有依赖） | 高密度结果的批量传输候选 | 不能自动解决事务、租约、重试去重或大表索引成本 | 由写入 profiling 决定，不预设必然更快 |

**Hyperscan 关键语义（官方 5.4.1 文档）：**

- `hs_compile_lit_multi` 按字面量编译，避免把关键字中的 `.`、`*`、括号解释成正则；该 API 自 5.2.0 起提供。Python `hyperscan` 0.9.1 已暴露 `compile(literal=True)`，但封装本身仍有下述输入边界需要验证。
- `HS_FLAG_SINGLEMATCH` 在 block 模式下限制同一模式 ID 在一次扫描内最多报告一次；不需要 start-of-match，不启用与之不兼容的 `SOM_LEFTMOST`。
- `HS_FLAG_PREFILTER` 的超集保证是针对其输入表达式语义，不是针对任意 Python `regex` 表达式。不能把原配置原样传入后宣称不漏报。
- 扫描结果顺序不能替代当前规则顺序；只采集 ID，最终按原规则位置输出。
- 首选每行一个 block。stream/vectored 模式的扫描边界不是业务日志行边界，见第九节。

### 平台、版本与许可证核验

公开包元数据与构建配置核验截至 2026-10-28，**不是本项目安装成功的报告**：

| 项目 | 核验结论 | 落地约束 |
|---|---|---|
| Python `hyperscan` 0.9.1 | 2026-10-08 发布；有 CPython 3.12 的 Linux glibc/musl x86_64、aarch64，macOS x86_64/arm64，以及 Windows AMD64 wheel | 本机 Windows x64 有可选包，但仍需真实安装、CPU 适配与回归；未见 cp312 Windows ARM64/32 位 wheel |
| 0.9.1 绑定的内核 | 构建配置固定 Unix VectorScan 5.4.12、Windows Intel Hyperscan 5.4.2 | 同一 Python 包版本不代表跨平台使用相同内核；两端分别记录、测试 |
| VectorScan 5.4.13 | 独立发行版日期 2026-08-23；核心面向 x86、ARM NEON/ASIMD 和 Power VSX | 核心可编译平台不等于 wheel 覆盖；不默认把它替换进 0.9.1 轮子 |
| 许可证 | Python 绑定 MIT；VectorScan 与 Intel Hyperscan 5.4 系列 BSD-3；VectorScan 项目说明 Intel 5.5 起转为 IPL | 优先评估 BSD 系列，锁版本并审阅发行包内全部许可证/NOTICE；不把 MIT 封装当成内核授权 |

**封装边界已复现：** `python-hyperscan` v0.9.1 的 `extension.c:620–644` 在 literal 编译分支用 `strlen(expressions[i])` 填充长度。2026-10-28 在本机 Windows wheel 上实际编译 `foo\0bar` 后扫描 `foo`，错误报告该 ID 命中，证实 NUL 截断。因此原型将含 NUL 的关键词整条规则送入兼容通道，空词走恒真逻辑；若后来使用接收显式长度的薄原生封装，必须单独测试该边界。

`pyahocorasick` 2.3.1 的 `iter()` 为逐项迭代；`ahocorasick-rs` 1.0.3 的 Python API 是列表返回。此差异影响中间结果内存，不代表迭代接口已消除重复事件 CPU 成本。

## 八、准确性是优化的不变量

### 8.1 不得改变的行为

1. 每个规则 ID 对一行最多一个结果；不同规则使用相同模式仍分别返回，保持输入规则顺序。
2. 关键词 `any` 返回配置顺序中第一个命中的原始词；`all` 全部存在才命中，并返回第一个配置词。重复词、重叠词、空字符串都按当前行为处理。
3. 不敏感关键词继续使用 Python `str.lower()`，不是 `casefold()`，也不是原生库的 caseless。对每行及每个关键词分别执行与当前相同的转换，再作精确字面量扫描。
4. 正则继续用当前 `regex.search` 获得 `matched_text`、named groups、可选组 `None` 与第一处匹配；阈值仍用 Decimal，结果的 severity/tags 不变。
5. 文件编码、成员路径、行号、file_glob、原始行截断标志、取消、重试和租约语义不变。只在解码后的同一逻辑行上优化。

**完整性边界：** 当前正则超时会跳过规则。保留相同超时策略不等于证明所有理论匹配都已找到，也不能保证两次运行在不同调度下发生完全相同的超时。测试必须单独统计超时，不把超时样本算作完整性验收成功；若要求超时后也绝不漏结果，需要另行确认隔离重处理与不完整状态策略，不能通过缩短超时实现提速。

### 8.2 三类路由

- **精确关键词通道：** 字面量存在性与 any/all 可直接算出最终结果，不必再调用 `_keyword_hit` 做第二遍相同子串搜索。
- **安全候选正则通道：** 只接受已证明正确的必需字面量条件。条件不满足才跳过，满足后仍交给原 `regex` 复核。
- **全量兼容通道：** 无法证明安全的表达式、原生库不支持的输入或扫描未完整结束，都回到原路径，不返回空候选伪装成无命中。

首版采用完整表达式语法白名单或精确识别的规则模板；第三方 parser 只是解析工具，不是跨方言正确性证明。拒绝旧方案直接依赖 `re._parser` 理解 `regex` 全语法。

- 合法拼接中的必需条件可取 AND；合法分支可取 OR；最小重复次数为零的子表达式不提供必需条件。
- 条件可保守放宽为 True，不能凭经验收紧。条件过多时放宽或整条回退，不展开指数级 DNF。
- 未认证的内联标志、模糊匹配、回溯控制或其他扩展出现于任意位置时，整条规则回退，不只是忽略局部节点。
- 首版对正则 `i` 使用兼容通道；之后可以认证“必要字面量与当前输入均为 ASCII”的专门通道，遇非 ASCII 行重新回退。不能以字面量是 ASCII 推导整条 Unicode 匹配安全。
- 关键词合法 Unicode 文本可转换为 UTF-8 做区分大小写的字节字面量扫描；若规则或输入不能按这一约定编码，使用兼容路径，不能静默忽略字符。

以下审查反例必须永久保留：`TITLE/i` 对 `tıtle`、`STATUS=/i` 对 `ſtatus=`、`ERROR{e<=1}` 对 `ERROR`、`(?ai:ERROR)` 对 `error`。旧方案在四者上均由一条真实命中变为零条。

## 九、重点提速设计：减少工作量，而不只是更换库

### 9.1 关键词一次扫描直接求值

- 编译期为唯一的 `(大小写通道, 规范化字面量)` 分配 literal ID，记录它对应的所有规则、any/all 关系和配置词顺序。
- 每行只准备一次原文、一次必要的小写文本；不敏感关键词本身仅在编译期规范化。
- 扫描只需要“哪些 literal ID 出现过”，不要所有位置。由命中 ID 更新规则状态，避免扫描结束后再对全部 5,000 条规则作 Python 遍历。
- `all` 对去重后的必需词计数，重复配置词不要求多次出现；空词恒真。`any` 不能按原生回调先后顺序决定 `matched_text`。
- 不去掉合法业务规则；只共享扫描状态，并按规则 ID 展开结果。

### 9.2 安全正则条件共享扫描

- 将认证的正则必需字面量与关键词合并到同一组字面量数据库，复用一次命中状态。
- 例如 `cost_ms=(?P<cost>\d+)` 可使用 `cost_ms=`；以元字符开头不代表不可过滤，`\d{1,3}-benchx001=(?P<x>\d+)` 仍可在已认证模板中使用 `-benchx001=`。
- 多个安全条件使用 AND/OR 公式比单个“最长词”更有区分度。所有规则仍保留精确复核，不让公式替代阈值判断。
- 先测**按执行时间加权的可过滤覆盖率**和每行精确正则调用数，而不是只数“有 hint 的规则占比”。高成本 fallback 比大量廉价规则更影响上限。
- 提高 `min_hint_length` 会使更多规则回退，候选可能增加；不能当作固定的提速方向。

### 9.3 同一模式复用搜索，规则结果不合并

可评估按 `(pattern, flags, timeout_ms, 引擎版本)` 共享已完成搜索的结果，再按每条规则分别执行阈值和输出。不同超时预算不合组；超时结果不能作为多条规则的“无命中”复用。

本轮只运行既有生成器做结构核算：5,000 条规则中有 2,010 条关键词规则、3,008 个按大小写通道去重的关键词字面量；2,990 条正则仅有 2,978 个不同执行键，三个重复组各含五条规则。因此该合成样本每行最多只省 12 次正则执行，**不能把搜索复用当作主要数量级收益**；真实规则需重新统计。

### 9.4 原生有界候选与逐行批处理

- B 路线使用 literal ID＋`SINGLEMATCH`，重复文本不再向应用返回同一 ID 的所有位置。若使用 AC，则必须在物化前有输入/事件界限，或使用可中止的迭代扫描；预算耗尽时把未确定规则加入候选，不能丢结果。
- 原生回调只写位图/计数器，不构造 Python 元组。若 Python 绑定每次回调的开销已显著，再引入 C 路线的薄原生封装。
- 5,000 个规则的候选位图为 625 B/行，1,024 行为 640,000 B；这只计算规则候选矩阵，不含可能更多的 literal ID、文本、匹配结果和原生数据库。批大小同时受字节数限制。
- 建议原型矩阵为每批 256/1,024/2,048 行、输入字节上限 1/4/8 MiB，作为待测参数而非既定默认。一条长行走受控单行路径，扫描预算只触发保守回退，不截断原评测文本。
- **一次跨语言调用处理多行，不等于一次 `hs_scan` 扫描多行。** 原生层内部仍逐行调用 block 扫描并重置 single-match 状态；直接拼接或用 vectored 扫描整批会改变锚点/跨行语义，且同一 ID 后续行可能被抑制。
- 原生扫描返回结构仍带稳定的行索引；精确复核、结果组装和入库使用原成员/行号，不把 offset 直接当字符索引或业务行号。
- 批次间以及慢行兼容路径需要保留当前心跳和取消检查机会；不能为了摊薄调用让一个原生批次长期占住租约。

审查中 64 个嵌套字面量＋4 KiB 重复行产生 260,128 条位置记录，旧方案单次约 45.7 ms，原路径约 0.105 ms。该例不是通用测速结论，而是必须加入的回退和内存边界门禁。

### 9.5 缓存与对象分配

- Worker 内缓存经过验证的规则集、字面量数据库和执行计划；规则版本键可沿用 `(rule_set_id, version)`，前提是绑定规则版本不可变。容量同时观察 RSS，不能只按条目数推断安全。
- 原生数据库编译缓存与 scratch 工作区分开；scratch 按实际执行线程独立使用，不在每行创建。持久化数据库若跨进程/宿主复用，还需校验库版本、CPU 目标和编译选项，首版不做跨机器二进制缓存。
- 只对真实命中创建 `RuleMatch`/`MatchRecord`，避免负例路径分配字典。若输出对象成为主要成本，可评估内部轻量记录，但公共结果字段和边界验证不变。
- 仅当真实日志有高重复率，再评估字节容量有界的整行精确结果缓存。键必须包含规则版本和完整文本，不能仅凭哈希判等；含超时/扫描失败的结果不缓存，路径与行号在使用时重新绑定。

### 9.6 文件级多进程优先

沿用现有文件任务队列扩展 Worker 进程：单机开发按 1/2/4/6 测扩展曲线，生产按第十六节的 ≥5 台 16 vCPU/32 GiB Linux 池以 `docker compose --scale worker=N` 水平复制。不增加逐行跨进程消息，也不先把一个压缩成员切成多份。数据库和解压/复制需要预留 CPU 与 I/O 配额。是否继续加进程由吞吐、p95、RSS 和存储等待共同决定，不要求为每个 Worker 盲目指定独占核，也不承诺线性。

## 十、端到端效率：写入与解压必须一起验收

| 阶段 | 优先测量 | 有证据后才采取的动作 | 不允许的捷径 |
|---|---|---|---|
| 源复制 | NAS 带宽、复制耗时、并发读取、续租间隔 | 调整复制并发和本地盘容量，保留分块续租 | 关闭只读守卫、根路径校验或源文件一致性检查 |
| 解压/解码 | 不同格式的字节吞吐、成员数、长行开销 | 按格式评估成熟流式库，保持解码结果和预算 | 全包读入内存、删除预算、改变替代字符/行边界 |
| 精确评测 | 每行候选数、fallback 时间、超时、对象分配 | 上述 B/C 路线；仅在瓶颈确认时扩展认证语法 | 丢规则、改大小写语义、减少 timeout |
| 写库 | 每批连接/执行/提交时间，WAL、锁等待、表/索引大小 | 比较现有 insert 与 psycopg COPY，按记录数和字节数双限批次 | 无界异步积压、降低持久性、跳过租约/重试隔离 |
| 查询与留存 | 亿级表查询计划、清理时间、备份恢复窗口 | 另立迁移评估分区与保留期，测读写权衡 | 为测速删除必要索引或擅自丢历史结果 |

写入吞吐不足时，批量 1,000/2,000/5,000 都需实测，而非默认越大越快。使用 COPY 前必须验证与租约栅栏、回收清理、重试和事务原子性兼容；更快传输不是正确性证明。需要并行写入时只允许有界队列和背压，并保持任务完成与所有批次提交的顺序。

不再采用“低于 20,000 rows/s 且 PG 未饱和，所以 DB 不是瓶颈”的旧 gate。低吞吐也可能来自锁、网络或提交等待；CPU/磁盘总体不饱和不能排除这些原因。

## 十一、性能可行性模型与目标档位

### 11.1 真正的提速上限

每行评测成本由规范化/扫描、候选正则精确执行、fallback、命中结果构建组成；库名称不决定这些项的比例。

若基线中无法加速的时间比例为 `f`，即使其他部分成本降为零，Amdahl 上限也只有 `1/f`：

| 保持不变的时间比例 | 理想提速上限 | 对本项目的含义 |
|---|---:|---|
| 70% | 1.43× | 只优化关键词而让主要正则全部照跑，无法得到数量级收益 |
| 35% | 2.86× | 若仍有大量高成本兼容规则，换扫描库不解决根本问题 |
| 10% | 10× | 需要真正移除大部分精确调用和解释器成本，而非仅缓存编译 |

表中的比例是分析情景，70% 来自本合成样本的近似拆分，不是对真实规则的承诺。匹配输出本身还要求至少处理实际命中数量；极高命中率时不可能完全消除结果构造和写入成本。

### 11.2 一亿行目标所需能力

| 目标窗口 | 至少聚合日志行/s | 若密度为 2.3278，至少结果行/s |
|---|---:|---:|
| 24 小时 | 1,157.41 | 2,694.21 |
| 8 小时 | 3,472.22 | 8,082.64 |
| 4 小时 | 6,944.44 | 16,165.28 |
| 1 小时 | 27,777.78 | 64,661.11 |

这些是容量要求，不是预测。生产口径已确认目标为 **8 小时档**（第十六节）：它要求聚合 3,472 日志行/s、约 8,083 结果行/s；24 小时档作为最低验证兜底，4 小时档必须先证明写入侧能持续 16,165 结果行/s。在目标环境实测后再承诺交付窗口，并为启动、规划、尾部任务和负载波动预留余量。

聚合吞吐受 CPU 评测、解压/源读取、结果写入共同约束；例如写库可持续速率为 `W`、每日志行平均输出 `q` 条，则日志吞吐不可能超过 `W/q`。这些是上界约束，不是把各阶段峰值取最小就能得到真实吞吐；当前同步 Worker 内复制、评测和写入等待仍会累加。

按 128 B/行，一亿行约为 12.8 GB 解压文本；不能把这个样本与 500 GB 输入批次混为一谈。不同压缩率、行宽和命中密度必须独立测量。

## 十二、准确性与性能验收矩阵

### 12.1 正确性：先证明不漏，再测快

- 冻结优化前参考求值器，不让它调用候选模块。端到端 oracle 显式选择参考路径；测试故意漏候选、错字段或打乱顺序时，必须失败。
- 小型穷举＋生成式差分覆盖 Unicode、内联 flags、模糊语法、空/重复/嵌套关键词、any/all、可选组、Decimal 边界、disabled 规则、不同 timeout，以及一行内多个正则匹配位置。
- 认证语法需要逐条转换规则的超集论证，随机测试只能找反例，不能代替证明；无法论证的模式继续兼容通道。
- 参考与优化比较完整 `RuleMatch` 有序列表，不只比较总数。入库按文件/成员/行号/规则 ID 对账业务字段与重复记录，不把数据库自增 ID 或创建时间当应相等字段。
- 保留重复规则负载；修复 manifest 按规则身份的期望结果，加入“删掉一条应有命中必须失败”的测试，不再只检查命中上限。
- 批处理边界覆盖空行、无结尾换行、CRLF、长行、跨成员、相同规则连续多行命中、`^/$` 与 `m/s` 标志；确保 single-match 只作用于一行。
- 原生扫描失败/中止、编码不适配、编译失败时验证不漏的回退；同时断言快路径实际启用并有计数，防止“全部回退也全绿”掩盖优化失效。
- 超时、取消、租约丢失、重试与 partial 档案独立验收，不把它们混入成功完整结果统计。

### 12.2 性能：分层定位，最终看全链路

| 维度 | 必测组合 |
|---|---|
| 规则 | 真实 5,000+；合成可过滤；高 fallback；大量相同模式；大量不同模式但相同 hint |
| 输入 | 128 B/512 B/1 KiB、真实 p99 长行、现有截断边界；中英文及特殊 Unicode |

| 并发 | 同宿主同配额 1/2/4/6 Worker；生产按 5 台 16 vCPU/32 GiB 节点 × 每节点多副本灰度（16.5/16.6），PG 配额和表状态记录在案 |

### 15.2 首版认证语法及必要条件证明

仅接受以下**完整表达式**，不是从任意正则中猜一个片段：

1. 非空 ASCII 字面量 `L`，字符仅为字母、数字、空格及 `_ = : / , @ % ! -`。这些字符在默认正则语义下没有元字符作用，因此 `search(L)` 命中必然要求文本包含 `L`。
2. `L(?P<name>\d+)` 或 `L(?P<name>\d{m,n})`，可在最前面追加 `\d{a,b}`。数字范围及组名必须完整符合窄模板，表达式自身先由原引擎验证。拼接中 `L` 不受量词、分支或可选组控制，故任意成功匹配都包含 `L`。
3. 外层 `i` 或任何未认证语法整条规则回退；外层 `m/s` 对上述不含锚点和点号的两类表达式不改变必要字面量。禁止将此证明推广到内联 flags、模糊匹配、分支、回溯控制或其他 `regex` 扩展。

筛选只使用必要条件，不能替代 `regex.search`、首处匹配选择、named groups、可选组 `None` 或 Decimal 阈值。关键词则使用 Python `str.lower()` 后的精确 UTF-8 字面量存在性：有效 Unicode 的 UTF-8 编码保留完整字符串的子串关系；不使用原生 caseless，也不使用 casefold。

### 15.4 五轮交错 A/B 实测

[`bench_multimode.py`](../service/scripts/bench_multimode.py) 只测规则求值，不运行旧数据库基准。每场景以相同冻结输入串行进行五轮 AB/BA；每轮计时后，另用独立编译的原求值器逐行比较完整有序 `RuleMatch`。计时期间只累加结果数量；计时外对账不计入吞吐。出现正则超时、原生异常回退或零原生扫描即判无效。

| 合成场景 | 规则 / 输入行数 | 行宽 | 每次遍历结果数 | 原路径中位秒 | 原型中位秒 | 原型行/s | 原路径/原型耗时比 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 稀疏，初测 | 5,000 / 500 | 128 B | 800 | 2.044389 | 0.0083165 | 60,121 | 245.82× |
| 稀疏，扩大十倍复核 | 5,000 / 5,000 | 128 B | 8,000 | 20.367484 | 0.0779123 | 64,175 | 261.42× |
| 全规则密集命中 | 5,000 / 500 | 128 B | 2,500,000 | 12.471840 | 13.053137 | 38.30 | 0.955×，耗时增加 4.66% |
| 正则全部兼容且密集命中 | 5,000 / 500 | 128 B | 2,500,000 | 12.369606 | 12.926122 | 38.68 | 0.957×，耗时增加 4.50% |
| 64 个嵌套短词重复输入 | 64 / 500 | 4 KiB | 32,000 | 0.0457365 | 0.0812398 | 6,155 | 0.563×，耗时增加 77.63% |

**解释与证据边界：**

1. 稀疏场景有 2,000 条关键词、3,000 条可认证正则，1,500 个不同正则执行键及 2,004 个字面量 ID，90% 行为普通负例。每行精确正则调用从 3,000 降到平均 **0.8**，所以这个合成样本收益很大；不是“换库普遍快 261 倍”。它与前五节既有 e2e 生成器不同，也不是已取得的真实规则集。
2. 扩大样本后的原型五轮耗时为 **0.075618–0.080093 秒**，参考为 **20.330205–20.501170 秒**；仍然是短时原语实验。原型编译含配置复制与参考正则编译，为 **0.328983 秒**，参考编译为 **0.164880 秒**，均排除在上表稳态计时外；没有清理进程内正则缓存来模拟冷启动。
3. 密集与高兼容场景刻意共享少数模式但保留全部合法规则 ID，每行必须构造 5,000 个独立结果；无法通过减少负例复核获益，候选集合与排序反而有成本。高兼容测试同时密集命中，**不能据此隔离估算真实低命中 fallback 的代价**。
4. 重复场景每行仅产生 **64 次原生回调**，而非旧 AC 方案的 260,128 个位置元组；已解决位置列表膨胀，但 Python 回调/集合/结果处理仍使其比原路径慢约 78%。目前不自动按负载切换引擎；原型不应作为统一默认路径。
5. 五份报告共完成 **35,000 次计时外逐行完整对账**，未遇超时或原生异常回退；`stats` 累计包含计时与对账两类调用，每轮各一次，不能误当成一次输入的统计。静态兼容规则调用不等于原生失败回退。
6. 原生数据库 `size()`：稀疏两个通道共 **648,336 B**、重复场景 **13,032 B**；这些不是进程 RSS 峰值。尚未采集峰值 RSS、阶段 CPU/回调占比、p95、百万行持续运行或真实 IO/数据库瓶颈，因此未满足生产性能验收矩阵。

### 16.2.1 两处自我更正（实测推翻推导）

**更正一：每任务固定开销不是 32 秒，而是约 40 毫秒。** 用真实 `TaskProcessor`、内存假件（不连数据库、本地临时盘、`nas_read_only_policy=ignore`）拆解单任务各阶段，5,000 规则与平凡规则集对照差分：

| 阶段 | 1 规则 × 2,000 行 | 1 规则 × 20,000 行 | 5,000 规则 × 2,000 行 |
|---|---:|---:|---:|
| 守卫 + stat + 本地复制 | 18.0 ms | 19.7 ms | 13.8 ms |
| 归档打开 + 成员列举 | 20.0 ms | 20.7 ms | 12.7 ms |
| 解压 + 解码 | 6.0 ms | 52.8 ms | 34.2 ms |
| `file_glob` 成员判定 | 0.07 ms | 0.04 ms | 0.03 ms |
| `evaluate_line` | 2.3 ms | 30.1 ms | 7,327.4 ms |
| 结果对象 + 缓冲 | 0.45 ms | 4.0 ms | 7.5 ms |
| 假件写批 + 栅栏收尾 | ≈0 ms | ≈0 ms | ≈0 ms |
| 未归因（抖动） | 4.9 ms | 36.1 ms | 32.8 ms |
| **单任务合计** | 51.6 ms | 163.4 ms | 7,428.4 ms |

差分给出的固定项约 39–40 ms/任务、每行管线成本 36 µs，而 5,000 规则的评测斜率是 3.93 ms/行。也就是说**端到端时间几乎全在评测本身**，扫描优化的价值因此是直接的，不是“只是留余量”。既有 5,000 规则 e2e 报告里 51 行/s/Worker（对照微基准 255 行/s）的 5 倍差距，不能归因于管线拼接；可归因的两项是：该负载每日志行输出 2.33 条结果并带 Decimal 阈值（与我的稀疏合成 0.32 条/行不同），以及开发机并发抢占（16.2 实测 8 进程并行效率 68%、12 进程 56%）。两者都未在目标环境量化，仍是待测项。

**更正二：写入侧容量已有实测下界，不再是“唯一未测的量”。** 在同一台机器的 PostgreSQL 16（WSL2，经宿主 socket 连接）上，用真实 `PostgresMatchWriter` 向一次性库写入 128 B 级 `raw_line`、`tags`/`fields` JSON、`Numeric(38,10)` 与两条二级索引：

| 批次行数 | 1 客户端 行/s | 2 客户端聚合 行/s | 4 客户端聚合 行/s | 批次中位延迟（1 客户端） | 重试 `delete_for_task` |
|---:|---:|---:|---:|---:|---:|
| 1,000 | 32,546 | 53,926 | 96,851 | 28.4 ms | 2.9 ms |
| 2,000 | 37,199 | 65,566 | 106,508 | 49.4 ms | 3.1 ms |
| 5,000 | 34,423 | 61,102 | 79,546 | 147.6 ms | 4.8 ms |

对照容量要求：8 小时档需要 8,083 结果行/s、4 小时档需要 16,165 结果行/s，两者都低于单客户端实测写入能力，且 4 客户端聚合还有 6–13 倍余量。**结论：在本机 PG 上写入不是 8 小时窗口的闸门；COPY、分区与保留期评估因此不是本轮前置条件**，但这是开发机 WSL2 实例，生产 PG 规格、磁盘、WAL 与并发 40 写入者的表现必须按 16.6 重新测。批次 2,000 行优于 1,000 与 5,000，5,000 的单批延迟已升到 148 ms，默认 1,000 是合理起点而不是最优值。

**并发扩展实测（本轮，开发机 14 物理核 / 20 逻辑核，屏障对齐后只计评测耗时，5,000 规则稀疏合成）：**

| 进程数 | 参考评测聚合 行/s | 相对 1 进程的并行效率 | 筛选原型聚合 行/s | 相对 1 进程的并行效率 |
|---:|---:|---:|---:|---:|
| 1 | 255 | 100% | 64,175 | 100% |
| 2 | 505 | 99% | 134,563 | 105% |
| 4 | 899 | 88% | 253,956 | 99% |
| 8 | 1,378 | 68% | 394,957 | 77% |
| 12 | — | — | 428,813 | 56%（约 43 万封顶） |

单进程峰值 RSS 约 **68–69 MB**（含解释器、5,000 条规则、两个原生字面量库），8 副本合计不到 0.6 GB。**内存不是 32 GiB 机器的约束**；解压缓冲与批次缓冲的真实占用仍需在 Linux 节点测量，这里只是评测层下界。开发机 8 进程后明显亚线性（超线程与内存带宽），16 vCPU 生产节点不能按 16 倍外推。

**修正后的结论：在 5×16U 规模下，8 小时窗口在评测、写入两个口径上都有余量，但余量来自“加进程”，不是来自扫描优化；扫描优化决定的是余量大小与最坏情况是否可控。** 按实测：未优化评测 274 行/s × 40 进程（含 68% 并行效率折损）约 7,400 行/s，即 1 亿行约 3.7 小时；启用筛选后单进程 6.4 万行/s，同一窗口只需极少数进程，且能把 4 小时档压进写入实测能力之内。因此扫描优化的真实作用是：把 8 小时从“勉强达标”变成“有数倍余量”，抗住密集命中与超长行，并在规则数继续增长时不失速。这是第十三节阶段 4（薄原生批处理）在本轮被排除的原因。

### 16.4 P1 已实施项与实测结果（不掩饰未解决部分）

**已实施并实测：**

1. **回退路径不再每行重建规则子集**：改用预建的参考规则集与预建静态子集。实测无原生场景 1,000 行 4,117.8 ms → 3,702.9 ms（**+10.1%**）。这是本轮筛选层唯一可复现的性能收益。
2. **回调不再逐项累加计数**，改为按命中 ID 数一次推导；`literal_id` 按 `(大小写通道, 文本)` 全局唯一，跨通道不重复，部分扫描失败在累加前整体回退，不虚报。
3. **关键词候选按规则位置有序遍历**，统计口径（`regex_calls / compatible_rule_calls / literal_events`）与改造前保持一致，基准的 fail-closed 判定不受影响。
4. **等价性加固**：绕过模型校验构造的“关键词规则带阈值”不再走快路径（参考路径此时不产出结果），交回参考求值器；该分支有专门用例钉住。

**未解决（实测确认，不做掩饰）：**

| 负载 | 快路径/参考耗时比 | 成因判断 |
|---|---:|---|
| 全规则密集命中（每行 5,000 条结果） | 0.910×（慢 9.9%） | 两个子集求值 + 结果按位置排序的每行固定成本；输出构造本身是两边共同成本 |
| 全兼容密集命中（正则全部走参考） | 0.913×（慢 9.6%） | 同上，且字面量扫描无候选可省 |
| 64 个嵌套短词 × 4 KiB 重复行 | 0.571×（慢 42.9%） | 4 KiB 行上“编码 + block 扫描 + 64 次 Python 回调 + 集合/排序”压过 64 次 C 级 `in`；要消除需 C 路线的批处理封装，本轮明确不做 |

**因此筛选层不得默认开启，必须按规则集实测选路。** 另外补充一条测量事实：在密集/全兼容场景把样本降到 500 行 × 5 轮时，本机多次触发 50 ms 正则超时；隔离复测同样本 150 万次 `regex.search` 的**单次最坏耗时仅 4.22 ms、无一超过 5 ms**，且超时命中的行号每次不同——判定为每行构造 2,500 个结果对象期间进程被抢占（超时是墙钟期限），不是模式变慢。基准据此拒绝出报告，改用 100 行 × 3 轮的同口径对照。

**仍未做（不假装完成）：** 复用 reader 已解码字节避免二次 `encode`；长行分块与心跳机会；把 `native_scans / literal_events / fallback_lines / keyword_fast_matches / regex_calls` 导出为 Prometheus 指标；Worker 侧按 `(rule_set_id, rule_version)` 的执行计划缓存。这几项是 P1 进入生产（`shadow`→`auto`）的前置条件，且必须先在 Linux 节点与真实规则上完成 16.6 验收。

### 16.5 跨平台与部署契约

- **依赖声明（本轮已验证可解析）**：锁文件里 `hyperscan==0.9.1` 带 42 个 wheel，其中 cp312 覆盖 `manylinux2014_x86_64 / manylinux_2_24_aarch64 / musllinux_1_2_{x86_64,aarch64} / macosx x86_64+arm64 / win_amd64`；生产镜像基座 `python:3.12-slim-bookworm` 是 glibc，落在 manylinux 范围内。用平台标记把它作为运行时依赖，Linux 自动安装、Windows 自动不装并走 P2 回退：

  ```toml
  dependencies = [
    # ...
    "hyperscan==0.9.1; sys_platform == 'linux' and (platform_machine == 'x86_64' or platform_machine == 'aarch64')",
  ]
  ```

  `uv pip compile --python-version 3.12` 分别对 `x86_64-manylinux_2_28` 与 `aarch64-manylinux_2_28` 解析出该包、对 `x86_64-pc-windows-msvc` 解析为空，证明这一标记成立。现有 `prototype` 依赖组保留给 Windows 开发与差分测试。注意 `Dockerfile` 当前是 `uv sync --frozen --no-dev`，不会安装任何额外依赖组；改为运行时依赖后镜像构建会自然带上，无需再加 `--group`。真正的 Linux 导入与扫描仍需在目标节点跑一次（本轮未做）。
- **内核差异是事实，不是配置项**：同一绑定 0.9.1 在 Unix 链接 VectorScan 5.4.12、Windows 链接 Intel Hyperscan 5.4.2。字面量＋`SINGLEMATCH` 的存在性语义是两端共同的契约，但**性能数字只引用 Linux 生产节点**；Windows 只用于跑同一套差分测试。
- **运行期开关**：新增 `LOGHARVEST_RULE_SCREENING`（`off` / `shadow` / `auto`，默认 `off`）。`shadow` 同时跑参考与候选并逐行比对完整有序结果，只写参考结果，用于灰度前对账；`auto` 才启用快路径。原生不可用或数据库编译失败时记录一次 `rule_screening_disabled`（含原因）并继续以参考路径成功完成任务，任何情况下都不得让任务失败或返回空候选当无命中。
- **进程内生命周期**：数据库与 scratch 由每个 Worker 进程各自持有，不跨进程共享二进制；按 `(rule_set_id, rule_version)` 缓存执行计划，同时记录 RSS。
- **副本与内存预算**：16 vCPU / 32 GiB 建议先按 **每节点 6–8 副本**灰度。评测层单进程峰值 RSS 实测 68–69 MB（含 5,000 条规则与两个原生字面量库，稀疏场景库合计 648,336 B），8 副本不到 0.6 GB，因此 **32 GiB 的容量压力来自解压临时盘与批次缓冲，不是匹配状态**；真正的副本上限由 NAS 带宽、PG 写入和文件粒度决定，且开发机在 8 进程后已明显亚线性（12 进程并行效率降到 56%），不能按核数线性外推。
- **队列粒度**：1,000 文件 ÷ 40 副本 = 每副本约 25 个文件；尾部不均衡约为一个文件的耗时。不要为提升并行度而先把单个压缩成员切开，那会改变行号与记录语义。
